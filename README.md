### 2. 문자열 입력받기
- 구분자와 양수로 구성된 문자열 입력받기
- 잘못된 값을 입력받은 경우 IllegalArgumentException을 발생시킨다.

1. custom 구분자가 있는 경우 
숫자,쉼표,콜론,커스텀 구분자 이외의 값 예외처리
2. custom 구분자가 없는 경우
숫자,쉼표,콜론 이외의 값 예외 처리

예: "//;\n1;2;3" -> 커스텀 구분자는 세미콜론(;)이다

3. 계산 기능 구현

# 문자열 덧셈 계산기

## 기능 목록

### 입력

- [x] 덧셈할 문자의 입력을 안내한다.
- [x] `Console.readLine()` 으로 문자열을 입력받음.


### 계산

- [x] 빈 문자열을 입력하면 `0`을 반환.
- [x] 숫자 하나를 입력하면 해당 숫자를 반환한다.
- [x] 쉼표(,)와 콜론(:)을 기본 구분자로 사용한다.
- [x] 기본 구분자로 분리한 숫자를 더한다.
- [x] `//`와 `\n` 사이에서 커스텀 구분자를 추출한다.
- [x] 커스텀 구분자로 분리한 숫자를 더한다.


### 출력

- [x] 계산 결과를 `결과 : {결과}` 형식으로 출력한다.

### 예외

- [x] 음수가 포함되면 `IllegalArgumentException`을 발생시킨다.
- [x] 숫자와 허용된 구분자 이외의 값이 포함되면 예외가 발생한다.

### 첫번째 리펙토링

- 변경 내용
Calculator 클래스의 이름을 CalculatorController로 변경했다.
static 메서드였던 Start()를 인스턴스 메서드로 변경했다.
Start() 내부의 지역변수였던 InputView, OutputView, Logic을 private final 필드로 이동했다.

- 변경한 이유

기존 Calculator는 덧셈을 직접 계산하는 클래스가 아니었다. 실제로는 다음과 같은 프로그램의 전체 실행 흐름을 담당하고 있었다.

안내 메시지를 출력한다.
사용자의 입력을 받는다.
입력값의 계산을 요청한다.
계산 결과를 출력한다.

따라서 클래스의 실제 책임이 이름에 드러나도록 CalculatorController로 변경했다.

또한 InputView, OutputView, Logic은 메서드에서 잠깐 사용하는 임시 값이 아니라, 컨트롤러가 프로그램을 실행하기 위해 계속 협력하는 객체라고 판단했다. 그래서 지역변수가 아닌 필드로 이동하여 CalculatorController가 어떤 객체들과 협력하는지 코드에 드러내고자 했다.

final을 사용해 컨트롤러가 생성된 이후 각 필드가 다른 객체로 재할당되지 않도록 했다. 다만 final은 객체 자체를 불변으로 만드는 것이 아니라, 필드가 가리키는 참조의 변경을 막는다는 점을 알게 되었다.

- 리팩토링 결과

클래스 이름과 실제 책임이 이전보다 명확하게 일치하게 되었고, 컨트롤러가 사용하는 협력 객체들도 필드를 통해 확인할 수 있게 되었다. 기능을 추가한 것은 아니지만, 코드가 프로그램의 구조와 객체 간 관계를 더 잘 설명하도록 개선되었다는 점에서 좋은 방향의 리팩터링이라고 판단했다.

다만 현재는 다음과 같이 컨트롤러 내부에서 구체 객체를 직접 생성하고 있다.

private final InputView inputView = new InputView();

따라서 이 구조는 의존성 주입(DI)이나 의존성 역전 원칙(DIP)을 적용한 것은 아니다. 앞으로 객체 생성 책임을 Application으로 이동하고, CalculatorController는 생성자를 통해 필요한 객체를 전달받는 구조도 고민해볼 수 있다.

### 두번째 리펙토링

InputView가 출력 기능을 사용하지 않는다는 이유로 InputParser로 변경했지만, 
입력을 읽는 것은 사용자와 프로그램 사이의 입력 경계를 담당하는 View의 책임임을 알게 되었다. 
또한 Parser는 단순히 문자열을 읽는 객체가 아니라, 
문자열을 숫자 목록과 같은 의미 있는 데이터로 변환하는 객체라는 점을 이해했다. 따라서 현재 변경은 이름과 실제 책임이 일치하지 않으며, 
InputView로 되돌린 뒤 추후 InputValidator의 문자열 분석 로직을 별도의 Parser로 분리하는 방향이 더 적절하다고 판단했다.

### 세번째 리펙토링

- 입력과 파싱을 구분했음
- Parser가 실제로 `String` -> `List<Integer>` 변환 수행
- 파싱과 합산 분리
- `InputValidator`가 합계까지 계산하던 책임을 발견하고 Logic에서 합계하도록 변경

### 네번째 리펙토링

- parse 메소드가 너무길어 메소드로 역할이 잘 보이게 메소드분리 시작
- 그런데 메소드를 분리하면서 input의 길이인 `n`과 `numList`를 계속 메소드마다 반복해서
- 선언해서 쓰는게 불편했음 -> 그래서 필드에 올려 공통적으로 쓰도록했는데
- 그러나 `n`과 `numList`는 `InputParser`객체가 살아 있는 동안 유지해야하는 상태는 아님
- 한마디로 제3자는 `InputParser` 객체가 입력길이와 파싱 결과를 상태로 보관하는 객체인가?
- 라고 생각할수 있다는것
- 하지만 혹여나 `InputParser` 객체에서 동시에 두번 `parse()`가 호출되면 서로의 상태에 영향을 줄 수 있음
- 중요한 건 `Parser`가 본래 상태를 보관할 필요가 없는 객체라는 점
- --> `InputParser`는 무상태 객체로 만드는게 필요함

- 이후 `input`에 숫자만 있는지 확인하는 메소드도 추가해 `parse()`리펙토링


### 다섯번째 리펙토링

- 제일 큰 리펙토링 문제로는 `validate`패키지를 유지하느냐, 지우느냐 였다
- 우선 `parse()`메소드를 보면, 내가 만든 계산기는 `parse()`과정에서 구분자나 숫자
- 이외의 값이 들어오게되면 애초에 parse작업이 불가능하다.
- `parse()`과정에서 validate를 다 하다보니 굳이 패키지를 따로 validate를 빼서 하기엔 무리가 있다고 판단해 삭제를 진행하였다.
- 추가로 각 메소드와 클래스이름이 추상적이었던 `Logic`을 `Calculator`로, 내부 숫자합산 메소드이름도 `calculateSum`으로 바꾸었다.
